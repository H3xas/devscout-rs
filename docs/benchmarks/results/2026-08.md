## Defects this run found in its own method

1. **`refs` truncates below its own graph.** `INBOUND_CAP = 30` (src/query.rs) capped `refs MessageUrn` at 30 of
   54 edges — 14 files, not 18, while `impact <same file> --hops 1` returns all 19 from the same graph with `dropped: 0`. `--all` lifts only `OUTBOUND_CAP`, so no flag recovers it — all of R1's loss.
2. **`find` rows do not reach.** Its second output block is `path: class X; members` with no line, so `locate`
   and `e2e-retrieval` fail the reach rule. peers.md discloses this for `impact` only.
3. **Corrected: not a defect.** `impact MessageUrn.cs --hops 1` → `Metadata/Activation.cs` is a legitimate
   documented interface hop (`ifaceVia`, `ambiguousCount: 0`, gone under `--no-iface`) via a precise member edge, not an unqualified nested-name collision. The class is real elsewhere: bare-name lookups onto nested types the referencing site can't legally name have produced verified-wrong precise edges at other sites and one fully false impact result, tracked with a re-registered roadmap gate.
4. **The truth-set method is the one methodology.md already flags:** text-adjudicated reference sets cannot hold
   an inference-only reference, so `references` is graded on the baseline's own terms. Fixing it needs issue-derived merged-fix diffs, out of reach for this offline round.
5. **No pre-registered predictions**, and no `not_attempted` reason quoted from ripgrep's own docs for `impact` — the rg arm got a composed 4-call chain instead. For the next registered run to fix.

- **The void floor held.** 0/4 correct with no repository (1 partial on DS-02, 3 wrong); no ticket was

- **No index correctness advantage over the baseline.** The one cell where `index` out-scored `none`

  met. If the index has a case this run, it is on tokens, not correctness.
- **DS-04 was predicted to most favour the index — and it exposed a tool limit instead.** The index
  lane reported that the SQL stored procedures the ticket turned on live inside C# string literals,
  invisible to the symbol index; they had to be found with grep. The ticket meant to be the tool's best
  showing is where its blind spot showed.
- **The Opus token saving is real but thin** (see the token table): ~25k median, `index` cheaper on
  three of four Opus tickets — one run, both arms over budget, Sonnet side censored, so not yet a claim.
- **The disclosed gap that blocks the headline.** With five Sonnet cells unscoreable and the Sonnet
  index arm down to one lane, tool-vs-base for devscout **cannot be concluded from this run** — that is
  the cleanest statement the data supports.

One run, four tickets, one corpus, half its Sonnet lanes censored. These findings describe what
survived; the 5-run protocol is what would let any of them become a claim.
