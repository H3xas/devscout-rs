The corpus is a `git archive` export of the pinned commit, given a git directory whose `HEAD` is
that commit so the tree reads as a clean checkout of the pin, exactly what
[`bench/clone-corpus.sh`](../../../bench/clone-corpus.sh) produces. Each arm gets a fresh copy,
none carries a `.git/scout` directory, and no existing checkout is mapped.

```sh
git archive <release commit> | tar -x -C "$EXPORT"
CARGO_TARGET_DIR="$TARGET" cargo build --release --locked -j 4 --offline      # in $EXPORT
dotnet build tools/scout-semantic -c Release                                  # in $EXPORT
dotnet restore "$ORACLE_CORPUS/MassTransit.sln" -p:TargetFrameworks=net9.0
dotnet run --project tools/scout-semantic -c Release -- "$ORACLE_CORPUS/MassTransit.sln" \
  --root "$ORACLE_CORPUS" --out "$ORACLE/refs.jsonl" --units "$ORACLE/units.jsonl" \
  -p:TargetFrameworks=net9.0
cd "$CORPUS" && "$TARGET/release/devscout" map .
"$TARGET/release/devscout" audit --semantic "$ORACLE/refs.jsonl" --units "$ORACLE/units.jsonl"
"$TARGET/release/devscout" audit --semantic "$ORACLE/refs.jsonl" --units "$ORACLE/units.jsonl" --json
```

The scorecard runs from the bench root with the corpus at `bench/corpora/csharp`, so every
`rg` and `ast-grep` path carries the same prefix, and the same payload bytes, as in 2026-08.

## What this measures / does not measure

- **Resolver precision**: per-edge precision by tier, recall over in-tree member sites and by
  receiver kind, the external-receiver leak, fan-out, and the top-20 false-positive and
  missed-target tables, with the metric definitions, join rule and exclusions of
  [`methodology.md#resolver-precision`](../methodology.md#resolver-precision). Same corpus pin and
  oracle procedure as Runs 0-5.
- **Scripted scorecard**: the eight tasks of [`2026-08.md`](2026-08.md) (L1, L2, R1, R2, I1, I2,
  E1, E2) with the same commands, the same corpus pin and the same grading of recall, precision,
  bytes and wall time, for the arms devscout (this release), `rg` (skilled) and `ast-grep`
  (R1/R2 only). The truth sets are the ones that document fixed; see "Scorecard grading" below.
- **Not measured**: the agentic (model-in-the-loop) round, which stays the 0.2.0 measurement of
  2026-08; the peer roster beyond `rg` and `ast-grep`; any corpus other than the pin; repeat
  variance.

### Scorecard grading

Fixed here, before any 0.7.0 output exists, from 2026-08's definitions and its stored truth:

- **References.** Core set = the files naming the symbol as a whole word, minus its declaring
  file: R1 (`MessageUrn`) 18 files, R2 (`IJobService`) 8. `correct` at ≥75% of core with ≤2
  files outside core ∪ admissible (the declaring file is admissible); `partial` at ≥40%.
- **Impact.** Graded set = the seed's adjudicated hop-1 dependents: I1 (`IJobService.cs`) the
  same 8 files as R2's core, I2 (`IntervalRetryPolicy.cs`) the 5 files naming
  `IntervalRetryPolicy` beyond its declaring file. `correct` needs every graded file within the
  declared cap of 5x the graded set (40 and 25 rows); `partial` needs at least half.
- **Locate and e2e-retrieval.** `correct` names the primary file (`MessageUrn.cs`,
  `IntervalRetryContext.cs`, `InMemoryOutboxFilter.cs`, `BusHealthCheck.cs`). An output that
  omits the primary is `partial` when it names the other truth file 2026-08 credited, and a file
  set containing the 0.2.0 cell's carries that cell's grade.
- **Reach**, bytes (`tokens = ceil(bytes / 4)`), cold and warm-median-of-5 wall time, and tool
  calls as 2026-08 measured them. Before any 0.7.0 cell is graded, the grader is run over the
  stored 0.2.0 streams and must reproduce every 0.2.0 grade, recall and precision exactly.

`rg`'s impact cells are 2026-08's four-call chain (declared types of the seed, the files naming
them, the types declared in those files, the files naming any of those). 2026-08 reconstructed it
from stored streams; this run records the exact command lines with the results.
