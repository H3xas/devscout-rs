The corpus is prepared exactly as in the 0.7.0 run: a `git archive` export of the pinned commit,
given a git directory whose `HEAD` is that commit, so each copy reads as a clean checkout of the
pin. Each arm gets a fresh copy, none carries a `.git/scout` directory, and no existing checkout is
mapped.

```sh
git archive <release commit> | tar -x -C "$EXPORT"
CARGO_TARGET_DIR="$TARGET" cargo build --release --locked -j 4 --offline      # in $EXPORT
dotnet build tools/scout-semantic -c Release                                  # in $EXPORT
dotnet restore "$ORACLE_CORPUS/MassTransit.sln" -p:TargetFrameworks=net9.0
dotnet run --project tools/scout-semantic -c Release -- "$ORACLE_CORPUS/MassTransit.sln" \
  --root "$ORACLE_CORPUS" --out "$ORACLE/refs.jsonl" --units "$ORACLE/units.jsonl" \
  -p:TargetFrameworks=net9.0
cd "$CORPUS" && "$TARGET/release/devscout" map .
"$TARGET/release/devscout" audit --semantic "$ORACLE/refs.jsonl" --units "$ORACLE/units.jsonl"
"$TARGET/release/devscout" audit --semantic "$ORACLE/refs.jsonl" --units "$ORACLE/units.jsonl" --json
```

## What this measures / does not measure

- **Default lane, resolver precision**: the same figures, tables and pins as the 0.7.0 run, with
  the metric definitions, join rule and exclusions of
  [`methodology.md#resolver-precision`](../methodology.md#resolver-precision). `audit` scores
  `uses-member` edges only, so the new `bus-hop` edges are **excluded** from every precision and
  recall figure: they are candidate type relationships between a publish site and a handler
  declaration, and the oracle has no record kind that could judge one.
- **Bus-hop reach**: how many `bus-hop` edges the pinned corpus gains, their handler-evidence
  words, how many handlers each message reaches, how concentrated the hops are, whether the
  corpus supplied its own handler vocabulary, and that `--no-bus` answers exactly as 0.7.0 did.
  This is reach, not precision: as the changelog states, behaviour precision and recall of these
  routes are unmeasured, and this document measures neither.
- **Enriched lane (opt-in)**: the Run 7/8 tables (the enriched-lane audit, the tier-by-tier change,
  the registered shipping gate) at this tree, against a freshly produced and freshly admitted
  compiler-facts artifact. Like Runs 7 and 8 this is **consumer conformance only**: both lanes are
  scored against the same oracle output, not against independently verified truth.
- **Scripted scorecard**: the eight tasks of [`2026-08.md`](2026-08.md) (L1, L2, R1, R2, I1, I2,
  E1, E2) with the same commands, corpus pin and grading as the 0.7.0 run, for the arms devscout
  (this release, default lane), `rg` (skilled) and `ast-grep` (R1/R2 only).
- **Not measured**: the agentic (model-in-the-loop) round, which stays the preliminary 0.2.0
  measurement of 2026-08; the peer roster beyond `rg` and `ast-grep`; any corpus other than the
  pin; repeat variance.

## Registered predictions (2026-09-25, before any measurement)

### Default lane

Basis, three facts about this tree, each checked in the source before predicting:

- **(a)** `audit` reads only `uses-member` edges from `graph.json`; `bus-hop` edges are appended
  after every other kind, and the bus-hop feature changes no other edge kind or count (the
  changelog's "Every non-bus edge kind and count is unchanged from the same commit's non-bus map").
- **(b)** The compiler-fact enrichment is opt-in: with no admitted artifact, `map` produces the
  syntax-only graph.
- **(c)** The oracle's walker is unchanged since 0.7.0. Two things around it changed: a restore
  step now runs before the walk, and it acts only on a project whose assets file is missing; and
  the tool no longer ships its own copies of three MSBuild assemblies, so the registered SDK
  supplies them. This corpus is restored with `-p:TargetFrameworks=net9.0` before the walk, so
  every project has its assets file and the restore step should touch nothing; the walk runs
  under SDK 9.0.305, which the old copies never failed under (the 0.7.0 run used it), and the
  failure the change fixes needs a 10.0 SDK. The prediction is therefore that the walk, and so
  the oracle output, is unchanged.

`audit`'s text output now names the lane in its header (`lane syntax`) and carries an `unjudged`
column, and its `--json` tier objects an `unjudged` key and a top-level `lane` key. Those are
format changes, not figures:

### Scorecard grading

The 0.7.0 run's registered rules, unchanged, the references rule included: core set = the files
naming the symbol as a whole word minus its declaring file (R1 18 files, R2 8); `correct` at ≥75%
of core with ≤2 files outside core ∪ admissible, `partial` at ≥40%; impact graded set = the
seed's hop-1 dependents (I1 the 8 files of R2's core, I2 the 5 files naming `IntervalRetryPolicy`
beyond its declaring file), `correct` needs every graded file within 5x the graded set, `partial`
at least half; locate and e2e-retrieval `correct` name the primary file. One addition, fixed here
before any output exists: an output byte-identical to the 0.7.0 run's stream for the same cell
carries that cell's grade (this is what carries E1's adjudicated `partial`). Before any 0.8.0 cell
is graded, the grader is run over the 0.7.0 run's stored streams and must reproduce every grade,
recall and precision that run published.
